# Build With Codex Playbook

## 1. 目的

让不手写大部分代码的产品负责人，仍能稳定地指挥 Codex 完成一个可维护、可验证的产品，而不是得到一堆难以运行的代码片段。

## 2. 基本循环

```text
定义用户结果
    ↓
提供范围与验收
    ↓
Codex 检查现状并计划
    ↓
实现最小垂直切片
    ↓
自动测试 + 实际使用
    ↓
产品负责人判断
    ↓
记录实验并决定下一步
```

## 4. 推荐构建顺序

### Sprint 0

项目结构、依赖、环境、配置、测试框架和空页面。

### Sprint 1

用固定假数据贯通：输入概念 → 问题 → 回答 → 诊断报告。

### Sprint 2

接入真实 LLM、Schema 校验、超时、重试和固定评估案例。

### Sprint 3

SQLite 保存、历史页和失败恢复。

### Sprint 4

知识状态、反馈和真实 30 天实验。

## 5. 产品负责人如何审查代码交付

不必逐行判断语法，但必须确认：

- 能否按说明在干净环境启动；
- 数据从哪里来、去哪里、失败后在哪里；
- API Key 和用户数据是否安全；
- AI 输出是否经过校验；
- 测试是否覆盖用户行为；
- 代码是否把未来功能提前做复杂；
- 文档与实际运行是否一致。

## 6. 常用 Codex 指令

### 实现

> 阅读 00、02、05、33。实现提交回答到诊断报告的 P0 垂直切片。先保存回答，再调用可替换 LLM 客户端；严格校验 Diagnosis Schema；补充超时与无效 JSON 测试。不要实现追问、RAG、登录或多 Agent。实际启动并完成一次手工验证。

### 诊断问题

> 只诊断，不修改。复现该问题，定位数据流中第一个偏离预期的位置，用文件和测试证据说明根因，并提出最小修复方案与风险。

### 代码审查

> 审查本次改动是否满足 PRD 和完成定义。优先报告会导致数据丢失、错误画像、Key/隐私泄露、无效状态或缺少测试的问题。不要评价无关风格。

### 补测试

> 根据 24 和 29，为当前行为补充最少但足够的单元、集成和端到端测试。默认使用 Fake LLM，不调用真实 API。

## 7. 控制范围

当 Codex 提出额外架构或功能时，产品负责人问：

1. 哪个已观察到的问题需要它？
2. 不做会阻塞当前验收吗？
3. 是否能用更简单方式完成？
4. 它的测试和维护成本是什么？

没有充分答案就放入 Backlog，而不是本次实现。

## 8. Git 与任务纪律

- 一个任务对应一个清晰目标；
- 每次修改前检查工作区，不覆盖用户已有改动；
- 小步提交，提交信息描述用户结果；
- 不把 `.env`、数据库、用户导出和模型原始日志提交；
- 代码、测试与文档同任务更新；
- 遇到破坏性迁移先备份并明确确认。

## 9. 失败处理

如果实现不工作，不要让 Codex 反复重写整个项目。要求它：复现 → 收集证据 → 找第一处错误 → 添加失败测试 → 最小修复 → 重新验证。

如果模型质量不工作，先区分问题来自问题生成、参考知识、评估 Prompt、Schema、模型能力还是界面误导，再决定是否换模型。

## 10. 每周节奏

- 周初：选择一个核心假设和一个垂直切片；
- 周中：可运行版本与固定测试；
- 周末：真实使用、记录失败、更新实验日志；
- 只在证据支持时进入下一项。

## 11. 交付门槛

Codex 的“已写完代码”不等于完成。必须：应用可启动、主要流程可运行、测试通过、失败可恢复、文档准确、产品负责人实际试用并做出接受/修改/拒绝决定。
