# Founder 决策框架

## 核心约束

MVP 的稀缺资源是验证次数，而不是功能数量。任何工作都应回答：它是否更快、更可靠地验证“AI 能否帮助用户发现真实理解缺口”。

## 功能评分

对新想法按 0–3 分评分：

| 维度 | 问题 |
|---|---|
| 核心价值 | 是否直接改善费曼诊断闭环？ |
| 学习证据 | 是否产生可解释、可纠正的学习证据？ |
| 可验证性 | 两周内能否用指标判断有效？ |
| 风险降低 | 是否显著降低隐私、安全或可靠性风险？ |
| 成本 | 实现、维护和认知复杂度有多高？（反向计分） |

总分低于 9 不进入当前版本；涉及高风险数据的功能即使高分，也必须先通过隐私审查。

## 必须拒绝的信号

- 竞争对手有，所以我们也要有。
- 没有清晰用户行为或成功指标。
- 需要同时引入多个新基础设施才能成立。
- 把单次回答扩展成性格、能力或人生结论。
- 不能解释如何删除、导出、回滚或评估。
- 让界面更“完整”，但不改善核心实验。

## 决策分类

- Type 1：难以逆转或影响隐私/数据/模型安全。必须写 ADR，至少由产品与工程共同确认。
- Type 2：低成本可逆。设时间盒实验，记录结果即可。
- 紧急决策：先保护用户数据和可恢复性；24 小时内补齐记录。

## 每周产品审查

1. 本周最大的用户证据是什么？
2. 哪个假设被否定？
3. 哪个功能没有带来可测价值，应停止？
4. AI 错误中是否有新的系统性模式？
5. 下周唯一最重要的实验是什么？

## 文档增长规则

默认更新现有文档，不新增文件。只有同时满足以下条件才创建新文档：存在独立所有者、独立生命周期、明确读者，并且合并会导致实际操作歧义。文档数量本身不是进展指标。
