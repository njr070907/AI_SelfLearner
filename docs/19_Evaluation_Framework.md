# Evaluation Framework

## 1. 目的

判断产品是否真的帮助用户理解，而不只是输出看起来专业的报告。评估分为 AI 质量、产品价值、认知状态质量、安全、成本与性能。

## 2. 评估层级

```text
L1 Schema & Reliability
   输出能否稳定解析和恢复
        ↓
L2 Diagnostic Quality
   是否正确识别正确点、遗漏、误区和限制
        ↓
L3 Learning Value
   是否帮助用户发现漏洞并采取行动
        ↓
L4 Longitudinal Value
   是否随时间形成可靠、可修正的认知状态
```

## 3. AI 质量维度

### Accuracy

诊断与领域专家/参考标签的一致程度；重点检查关键误区的误报和漏报。

### Explainability

结论是否由用户原文证据支持，能否区分不同问题类型。

### Calibration

高置信度结论是否确实更可靠；证据不足时是否降低置信度。

### Helpfulness

下一步是否具体、相关、可执行，用户执行后是否改善复测表现。

### Safety

是否避免人格标签、越界建议、注入攻击和隐私泄露。

## 4. 指标示例

- 结构化输出成功率；
- 关键误区 precision / recall（小样本先人工统计）；
- 人工总体一致度 1–5；
- 证据引用准确率；
- “遗漏被误判为误区”的比例；
- 置信度分桶准确率；
- 建议相关度/可执行性评分；
- 平均延迟、P95 延迟、每会话成本。

## 5. 评估数据集

每个案例包含：

```text
case_id
domain / concept / difficulty
question
reference_points
user_answer
expected_accurate_points
expected_missing_points
expected_misconceptions
acceptable_variations
human_rationale
safety_flags
```

覆盖数学、编程、AI、经济学；每个概念至少有强答案、弱答案、误区答案和证据不足答案。

## 6. 人工评审

评审者先独立标注，不看模型分数。评分表：

- 核心判断正确性：1–5；
- 漏洞完整性：1–5；
- 误区是否有原文证据：是/否；
- 置信度合理性：1–5；
- 建议帮助度：1–5；
- 有无严重安全问题：是/否；
- 备注与期望修正。

对分歧案例保留讨论记录，不用强行制造唯一答案。

## 7. 产品实验指标

### 个人 30 天

- 完成会话数与使用天数；
- 同概念复测数；
- 诊断认可率；
- 被发现的新漏洞数量；
- 建议采纳与完成；
- 用户学习行为是否发生一项可描述变化。

### 5–20 人测试

- 首次闭环完成率；
- 7 日复用；
- 诊断反馈分布；
- “比普通聊天更懂我的学习”评分；
- 数据控制与边界理解度。

## 8. 版本比较

每次比较固定：相同案例、相同输入、相同模型配置（若可能）、盲评顺序。记录每维改善、回退、成本和延迟，不只看平均分。

## 9. 发布门槛

- 严重安全案例 0 个；
- 结构成功率达到目标；
- 关键误区不得因版本变更显著回退；
- 低置信度案例能够与高风险错误相关；
- 人工帮助度达到团队约定；
- 延迟与成本可接受。

## 10. 失败学习

所有高置信度错误、用户“不准确”反馈和解析失败自动进入候选回归集。修复必须说明根因属于：参考知识、问题设计、Prompt、模型、Schema、UI 误导或产品假设。
