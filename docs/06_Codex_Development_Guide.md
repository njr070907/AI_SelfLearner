# Codex 开发指南

## 1. 合作模式

项目采用“产品负责人做判断，Codex 完成实现与验证”的协作方式。Codex 不只是生成代码，还需保持范围、测试、文档和可运行性一致。

## 2. 每个任务的标准输入

产品负责人给 Codex 的任务应尽量包含：

- 背景：解决哪个用户问题；
- 范围：必须做与明确不做；
- 验收：用户可观察结果；
- 约束：技术栈、安全、数据和兼容性；
- 参考：对应文档与已有代码；
- 验证：期望运行哪些测试。

如果缺少非关键细节，Codex 应采用最小合理假设并记录；只有会显著改变产品方向时才请求选择。

## 3. Codex 工作步骤

### 3.1 先理解

1. 阅读 `00_Project_Context_For_Codex.md`；
2. 定位相关 PRD、架构和测试文档；
3. 检查现有代码、测试和未提交更改；
4. 用一句话重述目标和完成定义。

### 3.2 再计划

把任务拆成可独立验证的垂直切片，例如：领域模型 → 服务 → 持久化 → UI → 测试。计划中不加入无关重构。

### 3.3 小步实现

- 先贯通最小成功路径；
- 再补失败路径和数据校验；
- 每步运行相关测试；
- 避免一次修改大量无关文件；
- 保持模型供应商代码在基础设施层。

### 3.4 完成验证

- 自动化测试；
- 实际启动应用；
- 完成一次真实端到端会话；
- 检查数据库记录；
- 检查 Key、个人数据和日志泄露；
- 更新文档与 `.env.example`。

## 4. 开发原则

1. **先闭环，再扩展。**
2. **明确优于聪明。** 使用简单函数与显式数据结构。
3. **确定性代码编排 AI。** 保存、权限、状态转换不交给自由 Agent。
4. **结构化输出。** AI 返回必须经过 Schema 验证。
5. **保留证据。** 原始回答、Prompt 版本、诊断版本可追踪。
6. **失败可恢复。** 模型失败不丢用户输入。
7. **测试行为，不测试实现细节。**
8. **不未经授权扩大范围。**

## 5. 代码质量规则

- 公共函数和领域模型使用类型标注；
- 复杂业务规则写短注释说明“为什么”；
- UI 文件不放 Prompt、SQL 或供应商调用；
- 不吞异常，转换为明确的领域/应用错误；
- 依赖集中声明并锁定兼容范围；
- 测试使用固定 LLM 假实现，默认不调用付费 API；
- Prompt 存在独立版本文件，禁止散落在组件中。

## 6. AI 功能审查清单

- 输入是否只包含必要数据？
- 参考材料是否被当作不可信内容，而非指令？
- 输出 Schema 是否严格？
- 解析失败、超时、限流是否处理？
- 结果是否带证据、置信度和版本？
- 是否会从单次记录推断稳定人格？
- 用户能否理解并纠正判断？
- 新 Prompt 是否通过固定评估集？

## 7. 推荐任务粒度

好的任务：

> 实现“提交回答并显示结构化诊断”的垂直切片：保存 pending 回答，调用可替换 LLM 客户端，校验 Diagnosis Schema，成功后写库并展示；补充超时和无效 JSON 测试。不实现追问、PDF 和登录。

不好的任务：

> 帮我做完整 AI 学习软件。

## 8. 提交/交付说明模板

每次交付应说明：

```markdown
## 完成结果
- 用户现在可以做什么

## 关键实现
- 主要数据流与边界

## 验证
- 执行的测试和手工流程

## 已知限制
- 当前未覆盖的情况

## 下一步候选
- 仅列与当前闭环直接相关的 1–3 项
```

## 9. 禁止事项

- 未经请求创建复杂多 Agent 框架；
- 在测试中默认调用真实付费模型；
- 把 Key、用户回答或个人画像提交到 Git；
- 为追求“架构完整”引入微服务、Redis、队列等；
- 自动把 AI 输出写成不可逆的用户事实；
- 用大规模重写掩盖一个小功能修改；
- 只展示代码而不运行验证。

## 10. 产品负责人的审核问题

即使不手写代码，也应每次确认：

1. 这个改动强化了哪个核心价值？
2. 用户能否从界面完成并理解它？
3. 新数据未来是否有解释价值？
4. AI 失败时发生什么？
5. 诊断为什么可信，证据在哪里？
6. 如果删除这一功能，核心闭环是否仍成立？
