# 完整自学 MVP 进度面板

> 这是开发期间的唯一进度口径。每完成一个可验收阶段就更新一次，并同步到 `CURRENT.md`、`BACKLOG.md` 和开发日志。

## 当前总进度

**约 66% / 100%**

当前位置：**阶段 1「自学教学闭环」已合并为可操作路径；错题、复习与长期状态页面正在功能分支等待审核**。

预计剩余：**10–18 个有效工作日**。其中包含剩余页面 PR 审核、真实模型语义验收、集成修复和至少一轮 7 天连续试用；不包含未经批准的真实模型费用。连续试用需要真实经过 7 个自然日，不能由并行开发压缩。

进度不是代码行数，也不是测试数量，而是按“用户能否验收一条完整产品能力”加权计算：

```text
总进度 = Σ（阶段权重 × 该阶段已验收比例）
```

因此，工程底座和后端接口已经比较完整，不代表用户已经可以正常使用完整产品；前端学习路径、反馈/趋势、真实 AI 发布边界和 7 天试用仍是主要剩余工作。

## 读数规则：功能百分比不等于时间百分比

- **66% 是最终产品功能的验收权重**，不是已经消耗的日历时间，也不是剩余时间的倒数。
- 后端阶段完成时会一次性计入该阶段权重，所以百分比会在 PR 合并后跳变，不会每天匀速增长。
- 后端已完成、前端尚未接入的能力只按该阶段约 50% 计入；实验性真实模型适配器不等于可发布的真实 AI 学习功能。
- 12–20 个有效工作日是按人类协作速度估算的剩余工程量；前端、人工语义复核和 7 天试用可以部分并行，也可能因为等待验收拉长日历时间。
- 进度只有在 PR 合并、自动验证通过并满足阶段验收后才更新；不能用聊天轮数、工具执行速度或代码行数推算时间。

### 为什么阶段 1 已经是 100%

PR #58 已将后端管道接入学习页面，并完成以下用户路径，因此阶段 1 可以按用户可操作口径计满：

- `SessionView`、`DiagnosisView`、失败重试和 `submit_follow_up` 已接入；
- 回答序号、诊断证据、推荐动作和错误恢复状态均可见；
- 主题、窄窗口和页面级交互已有自动测试，本轮又在 8511 做了实际浏览器复验。

### 为什么阶段 4 不是 100%

事件历史、当前状态投影、状态重算、重复误区统计和用户修正事件的后端能力已经合并，所以阶段 4 按后端验收计入 60%；但前端还没有把这些结果做成可操作的进度/趋势/反馈页面，仍需用户路径验收，因此不能按完整阶段计入。

### 为什么新的总进度低于旧的 56%

旧口径把“后端接口完成”接近等同于“用户功能完成”，并把实验性真实 AI 基线和已有 UI 壳计入过多。最终 MVP 必须让用户从学习、诊断、错题、复习、反馈一路走通，因此重新按最终验收重要性和实际工作量分配权重。新口径不是倒退，而是把未完成的前端、真实 AI 发布边界和连续试用重新计回剩余工作。

## 开发时的显示格式

后续每次阶段性汇报都使用下面的简短格式：

```text
MVP 总进度：66% / 100%
当前位置：阶段 1 已完成 · 阶段 2–4 页面在功能分支等待审核
预计剩余：10–18 个有效工作日 · 另需真实经过 7 个自然日连续试用
本次变化：完成 X，验证 Y
下一位置：……
```

如果发现阶段拆分或权重需要改变，必须在本文件记录原因，并同步更新总百分比；不能为了让数字增长而临时改权重。
