# 数据迁移、备份与保留

## 1. Schema 版本

数据库使用单调递增迁移编号，迁移文件一经合并不得修改。应用启动时核对数据库版本：落后则给出明确迁移指令，超前则拒绝启动。

## 2. 迁移要求

每次迁移包含：目的、前置版本、升级步骤、数据校验、预计时间/空间、失败恢复和兼容窗口。危险操作采用 expand-and-contract：先加新字段/表并双读或回填，验证后再移除旧结构。

SQLite 大表重建必须在副本演练；生产迁移前备份，迁移期间防止并发写入。不得把不可逆删除伪装成普通启动迁移。

## 3. 数据版本

除数据库 Schema 外，下列对象也要版本化：认知模型 JSON、诊断 JSON、Prompt、评估数据集、导出格式。读取旧版本时使用显式转换器，保留原始版本，不在读取过程中静默改写历史数据。

## 4. 迁移验证

- 行数、主外键、非空、唯一性和枚举范围。
- 随机样本与边界样本前后语义一致。
- 应用新旧读路径在兼容期结果一致。
- 删除/导出/保留任务仍能处理旧版本。
- 迁移耗时、磁盘余量和锁时间在预算内。

## 5. 备份策略

- 每日一致性备份，重要迁移前按需备份。
- 备份加密并与主库分离；只有恢复角色可访问。
- 保留最近 7 个每日、4 个每周备份；总最长保留不超过隐私承诺。
- 备份成功不等于可恢复：每月恢复到隔离环境并校验。

## 6. 恢复流程

1. 宣布维护/只读，停止写入。
2. 确认目标恢复点和数据影响。
3. 在隔离位置恢复并运行完整性校验。
4. 应用必要迁移，执行冒烟测试。
5. 切换流量，观察错误和数据指标。
6. 记录 RPO、RTO、丢失范围与后续行动。

## 7. 删除与备份

用户删除后，在线数据及可定位派生数据立即进入删除流程；备份不做高风险逐条修改，而是在最长 35 天内淘汰。若从旧备份恢复，必须先重放删除墓碑，防止已删除数据重新上线。

## 8. 导出兼容

导出包包含 `manifest.json`、数据文件、Schema 版本、生成时间和校验和。禁止在导出中包含内部 Prompt、其他用户数据、密钥或仅供安全审计的内容。
