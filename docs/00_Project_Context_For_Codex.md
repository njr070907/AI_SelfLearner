# AI Growth Companion：Codex 项目总上下文

> 文档基线：MVP Documentation v0.1  
> 读者：Codex、AI Coding Agent、产品负责人、未来开发者  
> 当前阶段：研究型原型，先验证核心闭环，再扩展产品

## 1. 项目是什么

AI Growth Companion（AI 成长伙伴）是一个从学习场景切入、逐步建立个人认知模型的长期 AI 系统。第一阶段不是做课程平台、笔记工具或通用聊天机器人，而是验证一个关键命题：

> AI 能否通过用户对知识的主动解释，可靠地发现理解漏洞，并在多次学习记录中形成可修正、有证据、有置信度的认知模型？

第一版核心原型名为 **Feynman Intelligence Engine v0.1**。

## 2. 核心闭环

```text
用户输入知识点
    ↓
AI 生成费曼问题
    ↓
用户用自己的话解释
    ↓
AI 诊断正确性、机制理解与误区
    ↓
保存问题、回答、诊断与证据
    ↓
更新知识状态
    ↓
展示报告与下一步建议
```

MVP 的价值不在“AI 给了一个答案”，而在“AI 是否识别了用户自己没有意识到的问题”。

## 3. 产品长期路线

```text
Phase 1  AI Learning System
         真正学会知识：费曼诊断、知识状态、学习建议
                         ↓
Phase 2  Personal Knowledge System
         连接跨领域知识，形成个人知识结构
                         ↓
Phase 3  AI Growth Coach
         连接目标、能力、项目与学习行为
                         ↓
Phase 4  Personal AI Companion
         成为透明、可控、长期理解用户的智能伙伴
```

长期愿景不等于当前范围。当前只构建 Phase 1 中最小、可验证的认知诊断闭环。

## 4. 第一批用户与使用方式

- 第一用户：产品创建者本人，每天真实使用 30 天。
- 第二批用户：5–20 名有明确自学目标、愿意持续反馈的大学生或自学者。
- 初期领域：数学、编程、AI、经济学，便于覆盖概念、机制、应用与推理。
- 用户可直接输入知识点开始；材料导入属于后续增强，不阻塞核心实验。

## 5. 角色分工

产品负责人采用 **AI 搭建 + 人做决策** 的模式：

- 人负责愿景、范围、优先级、验收标准、真实测试和最终判断。
- Codex 负责代码结构、实现、自动化测试、文档同步和可运行交付。
- AI 的技术建议不能自动扩大产品范围。
- 产品负责人不必手写每行代码，但必须能看懂系统边界、数据流、风险和测试结果。

## 6. MVP 技术基线

为了快速验证，第一阶段默认：

- Python 3.11+
- Streamlit 原型界面
- SQLite 本地数据库
- LLM API（通过统一客户端封装）
- Pydantic/JSON Schema 约束结构化输出
- pytest 进行单元与流程测试

升级路线：

```text
Streamlit + SQLite
        ↓ 验证核心价值后
React/Electron + FastAPI + PostgreSQL
        ↓ 材料与检索需求成立后
对象存储 + Vector DB + RAG
```

不要在 v0.1 提前引入微服务、消息队列、复杂多 Agent、完整知识图谱或多租户系统。

## 7. 核心对象

- `Concept`：当前要解释的知识概念。
- `FeynmanQuestion`：针对概念生成的开放式诊断问题。
- `UserExplanation`：用户自己的解释，不等同于标准答案。
- `Diagnosis`：正确性、理解深度、缺失点、误区、追问和置信度。
- `LearningSession`：一次从出题到报告的完整交互。
- `KnowledgeState`：某概念随时间变化的掌握估计。
- `CognitiveEvidence`：支持某个认知判断的具体记录。
- `CognitivePattern`：跨多次证据出现的学习或思维模式。

## 8. AI 必须遵守的原则

1. 不因文笔、术语数量或表达流畅度直接判断理解程度。
2. 诊断必须区分“事实错误”“缺少关键机制”“表达不完整”和“证据不足”。
3. 重要判断必须包含依据与置信度。
4. 不用一次行为给用户贴人格标签。
5. 使用“目前证据显示可能……”而不是“你就是……”。
6. 用户可查看、纠正、删除 AI 对自己的判断。
7. 不确定时降低置信度并提问，不编造确定性。
8. 建议帮助用户做决定，不替用户做决定，也不制造依赖。

## 9. MVP 成功标准

核心成功标准不是页面数量或模型分数，而是：

- 用户认为 AI 指出的关键漏洞准确且具体。
- AI 对明显强答案、弱答案和常见误区能作出可解释区分。
- 同一知识点重复测试时能展示有意义的变化。
- 诊断记录可以被保存、重放和人工复核。
- 至少连续使用 7 天，并完成一轮 30 天个人实验。
- 用户愿意根据建议采取一次后续学习行动。

## 10. 明确不做

- 复杂账号、支付、社区、排行榜和商业化功能。
- 完整课程生产、公共知识库和内容市场。
- 自动职业规划、心理诊断或人格定性。
- 为“看起来先进”而构建多 Agent 编排。
- 在核心诊断未验证前开发完整桌面产品。

## 11. Codex 的默认执行顺序

1. 阅读 `00`、`02`、`16`、`23`、`33`。
2. 建立最小可运行项目和环境配置。
3. 先用固定假数据贯通 UI、领域模型和数据库。
4. 接入 LLM，强制结构化输出与错误处理。
5. 实现问答、诊断、保存、报告完整闭环。
6. 用 `29` 的测试案例和 `24` 的测试策略验证。
7. 记录 Prompt 版本与产品实验，不擅自扩展功能。

## 12. 完成定义

一次开发任务只有同时满足以下条件才算完成：

- 功能可从用户界面实际运行。
- 成功路径与关键失败路径有测试。
- 数据可以正确保存和重新读取。
- LLM 输出异常不会导致数据污染或界面崩溃。
- 使用说明和相关文档同步更新。
- 没有引入超出当前 Sprint 的无必要复杂度。
