# ADR：架构决策记录与初始决策

## 使用规则

ADR 记录重要且难以逆转的技术决策。状态为 Proposed、Accepted、Superseded 或 Deprecated。已接受 ADR 不修改历史结论；新建 ADR 替代它。

模板：标题、日期、状态、背景、决策、替代方案、后果、验证/复审触发器。

---

## ADR-001：MVP 使用 Python + Streamlit 单体

- 状态：Accepted
- 背景：需由小团队快速验证费曼诊断闭环。
- 决策：采用模块化 Python 单体，Streamlit 负责首版 UI。
- 替代：React + FastAPI、Electron。
- 后果：开发快、部署简单；复杂交互和独立客户端能力有限。
- 复审触发：出现第二类客户端或 UI 限制阻碍核心实验。

## ADR-002：MVP 使用 SQLite

- 状态：Accepted
- 决策：通过 Repository 隔离 SQLite；所有结构变更走迁移。
- 替代：PostgreSQL。
- 后果：本地优先、零运维；并发与远程多用户能力有限。
- 复审触发：真实锁竞争、多实例写入或生产高可用需求。

## ADR-003：LLM 厂商通过 Provider 接口隔离

- 状态：Accepted
- 决策：业务层只依赖内部接口；真实与 Fake Provider 均实现契约。
- 后果：便于测试、回滚和供应商切换，但需维护适配层。

## ADR-004：所有诊断使用结构化 Schema

- 状态：Accepted
- 决策：模型输出必须经版本化 Schema 校验后才能持久化和展示。
- 后果：可靠性和可评估性提高；开放式表达受约束，需设计降级体验。

## ADR-005：默认不记录用户正文日志

- 状态：Accepted
- 决策：运行日志只保存脱敏元数据和关联 ID。
- 后果：隐私风险降低；调试依赖可复现合成样例和用户主动提交的问题报告。

## ADR-006：MVP 不引入向量数据库和多 Agent

- 状态：Accepted
- 背景：当前核心假设不依赖复杂检索或自治协作。
- 决策：先使用当前会话和结构化历史；达到 39 中的触发条件后再评估。
- 后果：范围可控；P1 的长材料检索能力延后。

## ADR-007：用户纠错优先于派生认知结论

- 状态：Accepted
- 决策：用户否定的诊断保留审计历史，但不再作为确认事实参与默认聚合；重新启用须有新证据并明确提示。
- 后果：增强用户控制；聚合逻辑需要支持状态和证据追溯。

## ADR-008：数据库迁移采用前向兼容优先

- 状态：Accepted
- 决策：使用 expand-and-contract，结构回退不是默认恢复方式。
- 后果：降低数据丢失风险；发布过程可能需要兼容窗口。
